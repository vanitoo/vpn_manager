# Security Policy

## Поддерживаемые версии

До релиза `1.0` исправления безопасности применяются к актуальному `main`. Старые архивы, форки и произвольные commit SHA могут не получать обновления.

## Сообщение об уязвимости

Не публикуйте в открытом Issue сведения, которые позволяют:

- получить административный доступ к Telegram-боту;
- извлечь токены, API keys или cookie;
- обойти подтверждение платежа;
- получить или продлить VPN без авторизации;
- получить чужой subscription URL;
- читать чужие тикеты или сообщения;
- выполнить произвольный SQL/код;
- получить несанкционированный доступ к Remnawave;
- раскрыть персональные или платёжные данные.

Используйте GitHub Private Vulnerability Reporting, если он включён. Если приватный канал недоступен, сначала свяжитесь с владельцем репозитория без публикации exploit-кода и реальных секретов.

## Что приложить

- затронутую версию или commit SHA;
- компонент;
- условия и шаги воспроизведения;
- ожидаемое и фактическое поведение;
- оценку влияния;
- минимальный proof of concept без реальных данных клиентов;
- возможный способ исправления.

## Секреты

К секретным данным относятся, в частности:

- `BOT_TOKEN`;
- `REMNAWAVE_API_TOKEN`;
- RemnaNode secret/private keys;
- Reality private keys;
- YooKassa/Cryptomus/Lava/Platega credentials;
- nginx cookie и Basic Auth;
- `.env`;
- рабочая SQLite-база и резервные копии;
- subscription URL пользователей;
- логи с чувствительными идентификаторами и данными.

Не публикуйте их в Git, Issues, Pull Requests, скриншотах и диагностических сообщениях.

## Если секрет утёк

1. Считайте секрет скомпрометированным.
2. Отзовите или перевыпустите его в соответствующей системе.
3. Обновите production environment.
4. Перезапустите затронутый сервис.
5. Проверьте логи и связанные операции за период компрометации.
6. Если секрет попал в Git, удалите его из истории, но не считайте это заменой ротации.
7. Убедитесь, что старое значение больше не работает.

## Production рекомендации

- храните `.env` вне Git и ограничивайте права на файл;
- ограничивайте доступ к SQLite и backups;
- используйте HTTPS для Remnawave и subscription endpoints;
- не публикуйте административные порты без необходимости;
- разрешайте Telegram-админку только через доверенные `ADMIN_IDS`;
- ограничивайте состав операторов support-группы;
- регулярно обновляйте Docker images и Python dependencies;
- не отправляйте пользователю traceback и внутренние HTTP-ответы;
- резервные копии храните отдельно от основного контейнера;
- перед изменением интеграции проверяйте влияние на Remnawave 2.x и 3.x.

## Платежи

Успешная выдача VPN должна происходить только после подтверждённого статуса оплаты. Значение callback, URL возврата или сообщение пользователя `Я оплатил` само по себе не является доказательством оплаты.

Не храните полные реквизиты банковских карт. Используйте только данные и идентификаторы, необходимые для работы платёжного API и чеков.

## Subscription URL

Персональная ссылка подписки фактически предоставляет доступ к VPN-конфигурации и должна рассматриваться как чувствительный bearer-secret. Не выводите её в общие логи и административные рассылки без необходимости.

## Границы ответственности

Проект управляет Telegram-ботом и интеграциями, но безопасность всей системы также зависит от ОС, Docker, reverse proxy, Telegram-аккаунтов, Remnawave, DNS и платёжных кабинетов.
